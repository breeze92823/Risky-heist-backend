# Risky Heist — BACKEND (game server)

Frontend (3D client) lives at `../Risky-heist`. Colyseus + Mongo, ported from `C:\ThreeJS\Kayak-and-surf\Kayak-and-surf -backend` and reshaped for the heist game's save.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { token, username, pfp })`, client side `../Risky-heist/src/net.js`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable. `/health` for Legion; `/monitor` and the playground are dev-only.
- **Identity (Bloxity audit rule)**: the server never trusts an id from the client. `onAuth` sends the join option `token` (`Legion.SDK.auth.getToken()`) to `POST {BLOXITY_API_URL}/v1/auth/game-token/verify` (`Authorization: Bearer <token>`, body `{ gameSlug }`) and uses only the returned `user._id` (`src/bloxity.ts` `verifyToken`); a refused / missing token (or an unreachable Bloxity) is a guest, who is never loaded or saved. Display names of verified players come from Bloxity. `identify` re-verifies a new `token` after a mid-session sign-in / sign-out ("" = signed out); an id in a message is ignored. Tests fake Bloxity with `__setVerifierForTest` / `__setFetchForTest` (`test/server.ts` `fakeVerify`: token `tok-<id>` = account `<id>`; `test/Bloxity.test.ts`).
- **Bloxity reporters** (`src/bloxity.ts`, started by `installReporters()` in `src/index.ts`; each is a no-op unless the hosting variables are set): live rooms every 2 s (`POST {MATCHMAKER_REPORT_URL}/{BLOXITY_GAME_ID}/rooms`, `matchMaker.query`), game stats every 60 s and on SIGTERM (`POST {BLOXITY_API_URL}/v1/games/{BLOXITY_GAME_ID}/stats`, definitions in `STAT_DEFINITIONS`, values clamped to Boxity's per-type ceilings), hosted leaderboards every 30 s, changed scores only (`POST .../v1/leaderboards/hosted/{gameId}/report`, boards in `LEADERBOARD_BOARDS`: `rebirths`, `earned`, `maxfloor`, `stolen`). All read the server's own copy of each signed-in player's progress (never a client packet), report `legion_<id>` users, skip guests, use `Authorization: Bearer $BLOXITY_REPORT_TOKEN`. Env: `BLOXITY_API_URL` (default prod, only when missing), `BLOXITY_GAME_ID`, `BLOXITY_REPORT_TOKEN`, `MATCHMAKER_REPORT_URL`, `POD_NAME`/`HOSTNAME`.
- **Rewarded ads**: message `adReward` { token, placement } -> the server checks the token with `POST {BLOXITY_API_URL}/v1/ads/reward/verify` { gameSlug, rewardToken } and answers `adRewardResult` { ok, placement }; the client grants the reward only on `ok`.
- The Mongo doc is the signed-in player's save. The client still writes a local copy (`localStorage`) as its offline fallback; on join the server's save replaces it, and a new account (`noProgress`) adopts the local copy as its first save. A guest's (or a serverless session's) progress lives in the browser only.
- Messages client -> server: `saveProgress` (the whole snapshot, throttled client-side to one per ~8 s plus a flush when the tab hides/closes), `identify` (`{ token, username, pfp }` after a sign-in/out mid-session), `adReward`, `pose` / `setAvatar` (presence, see below; the client does not send them yet). Server -> client (private): `progress` (the saved doc, sanitized, + `serverTime`), `noProgress` (new account, guest, or no database: the client keeps its state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp` (Bloxity profile picture URL, http(s) only, max `PFP_MAX_LEN`, "" = none) plus presence.
- Saved progress shape (`PlayerDoc` in `src/db.ts`; the client's `heist/game.js` `state` as returned by `snapshot()`): `money`, `carryCap`, `unlocked` (base slots), `tool` (index into `TOOLS`), `owned[]` (tool indexes), `slots[] { id | null, stored }` (the base, in order), `carried[]` (treasure ids), `discovered[]` (the Index), `rebirths`, `daily { day, claimed[7], nextAt }`, `stats { stolen, heists, earned, busts, bestId, maxFloor }`, `spawns { rarity: epoch ms }`, `pending { rarity: bool }`, `lastSeen` (epoch ms; collectors are credited for the time away, capped client-side). Fields a save leaves out are kept as stored. The whole save is client-authoritative, Daily Gifts included (the client runs its own 24 h-of-play clock).
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`rebirths`, `earned`, `maxFloor`, `stolen`; the doc paths are in `LEADERBOARD_FIELDS`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS`. `connectDb` creates a descending index per stat. The client does not draw them yet.
- Room size and bases (`test/Bases.test.ts`): a room holds `ROOM_MAX_CLIENTS` = 6 players, one per hub plot (client `BASE.positions` has 6 plots; keep the two in step). `onJoin` gives each player the lowest free plot (`base`, 0..5, unique in the room; `freeBase` in `presence.ts`), kept until they really leave (a dropped connection keeps it through `allowReconnection`), then free for the next joiner; a 7th player is refused and the Bloxity matchmaker opens another room. What a base shows the others travels in the roster: `baseUnlocked` and `baseItems` (treasure id per slot, comma separated, "" = empty), set by the message `setBase` { unlocked, items[] } (cosmetic, bounded, guests included; separate from the saved progress). The client puts each owner's name and loot on their plot.
- Other players (client `src/avatar/remotePlayers.js`): the roster also carries `userId` (the account id Bloxity verified, "" for a guest; public on purpose, so a chat message's `userId` finds its character), `emote` (the portal emote id being played, "" = none; message `emote` { id }, `ID_PATTERN` or "") and `grounded`, `carry` (best carried treasure id, `ID_PATTERN` or ""), `riding`, `swing` (booleans), all set through `pose`. The look (`avatar`) is an opaque string the server only length-caps: clients must sanitize it before using any id (the client's `parseLook` does).
- Presence (`src/presence.ts`, `test/Presence.test.ts`): relayed through the roster as sent, only bounded. Roster fields `x`/`y`/`z` (feet, m), `yaw` (wrapped to -PI..PI), `speed` (m/s), `avatar` (Bloxity look JSON, at most `AVATAR_MAX_LEN`, never parsed). Messages `pose` { x, y, z, yaw, speed }, `setAvatar` { avatar }; the join options may carry `pose` and `avatar` too.
- `src/constants.ts` bounds must cover the client's `src/config.js` (slot / carry / tool / floor counts, currency up to ~1e33, treasure ids match `ID_PATTERN`). A contract change goes in both projects (and `test/Sanitize.test.ts`).
- Local end-to-end: run this server (`npm start`, no Mongo = `noProgress` for everyone) and the client with `npm run dev` (it defaults to `ws://localhost:2567`). Locally the player is a guest (no Bloxity token, nothing saved) unless the real SDK signs them in; the server tests are the way to exercise saves.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` (6) read from `src/constants.ts`. The SDK docs (https://docs.bloxity.io, "Multiplayer connection") say: `maxClients` = the room size (2-100), send `roomSize` in the deploy, never `seatCap` (the hosting page's `seatCap` wording conflicts with it; the SDK docs and this workflow's original template agree on `roomSize`). A full room makes the matchmaker open another. Needs repo var/secret `LEGION_GAME_ID` (= `risky-heist`) and secret `LEGION_DEPLOY_TOKEN`.
